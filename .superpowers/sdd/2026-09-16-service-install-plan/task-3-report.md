## What was implemented

### `crates/sapphire-framework-service/src/launchd.rs` (new)
- `label(app_name)` — `net.fireturtle.sapphire.<app>`, the repository owner's namespace,
  matching `Cargo.toml`'s `repository` (a LaunchAgent label is a global namespace).
- `agent_path(app_name, home)` — `~/Library/LaunchAgents/<label>.plist`.
- `escape(text)` — single-pass XML character-data escape: ampersand first, then angle
  brackets. Quotes are deliberately left literal: every dynamic value lands in a text node
  where quotes are legal, and the verbatim contract test demands a literal `"a b"` inside
  `<Arguments>`. Entity forms already present in the input are themselves escaped.
- `comment_safe(text)` — neutralises `--` runs (illegal in XML comments) so the app
  description can appear as an XML comment without making the file unparseable.
- `render_launch_agent(spec, ctx)` — plist with namespaced Label, per-argument
  `ProgramArguments` `<string>`s (launchd execs directly, no shell, so a space inside an
  argument needs no quoting), `RunAtLoad`, `KeepAlive`/`SuccessfulExit=false` (the
  restart-on-failure counterpart), `ThrottleInterval=5` (the `RestartSec=5` counterpart),
  description as an XML comment for `launchctl list`.
- Inline unit tests: agent path shape, escape single-pass proof (including the
  ampersand-entity-in-input case).

### `crates/sapphire-framework-service/src/windows.rs` (new)
- `escape(text)` — same single-pass text-node escape (3 entities), same rationale.
- `arguments(args)` — Windows command line: an argument containing a space is wrapped in
  double quotes so it survives `CreateProcess` splitting as one argument.
- `render_task(spec, ctx)` — Task Scheduler XML schema 1.2 with `LogonTrigger` (runs at
  logon, the user-level counterpart of a systemd user unit), `InteractiveToken` principal,
  `MultipleInstancesPolicy=IgnoreNew` (single instance), battery restrictions disabled,
  and `ExecutionTimeLimit=PT0S` (limit-free: the scheduler's default thirty-day kill would
  stop a long-running agent). Declaration is `encoding="UTF-8"`, self-consistent with the
  UTF-8 string this API produces — a `UTF-16` declaration on UTF-8 bytes is exactly the
  kind of mismatch MSXML rejects with an unhelpful message.
- Inline unit tests: escape single-pass proof, space-containing argument quoting.

## Tooling anomaly encountered (transparency)

- Mid-task, the file-writing tool channel **decoded XML entity sequences twice** in
  transit: literal `&` written via the tool arrived on disk as `&`, corrupting draft
  `escape()` implementations (no-op arms, a syntax error) and two test assertion lines.
  Detected by repr-level inspection; repaired programmatically (entities constructed from
  `chr(38)` in Python, never typed literally), every fix verified byte-exact by re-reading
  from disk. The committed state is verified by the test suite, `xmllint`, and repr
  checks; no residual mangling remains. Consequence: extra iteration cycles, no defect in
  the committed code. The golden files were generated by the compiler (test harness), not
  hand-typed, so they cannot have been affected.

## Design decisions (within the brief's constraints)

- **3-entity text-node escape, quotes literal.** The verbatim contract
  `rendered.contains("\"a b\"")` requires a literal quote in `<Arguments>`, and every
  dynamic value (exe path, args, description, label) is XML character data where quotes
  are legal unescaped. Escaping quotes would have broken the verbatim contract test.
- **`UTF-8` declaration.** `UTF-16` on UTF-8-rendered bytes is a mismatched-declaration
  booby trap; see windows.rs doc comment.
- **Description as XML comment in the plist.** launchd's plist schema has no description
  key I could attribute truthfully (a `ProcessDescription` key is not part of the schema);
  the XML comment is the place a human looks and the one place the XML grammar has room.
- **System scope stays Linux-only** (Task 1's `resolve_scope` refuses it off Linux before
  these renderers run); both new modules are user-level only, matching the brief.
- **Windows quoting covers spaces.** Embedded quotes/backslash sequences per the full
  MSVCRT argument-parsing rules are not handled — the spec carries plain args like
  `server run`; hardening to that would be its own task if real paths demand it.
